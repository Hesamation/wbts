# Optional external investigations: WBTS revival and fresh opportunities

Prepared November 14, 2026. These are proposed assignments for external agents, not agents launched here or a selected build. The human intends heavy agent-assisted execution and a hackathon demonstration. Do not reject an idea because an unaided developer would need several days; equally, a model-generated implementation estimate is not proof that a dependency works.

## Recommended arrangement

Run three different investigations in fresh external sessions: **1 WBTS mechanism/product reconstruction**, **2 fresh swarm opportunity**, **3 track/competitor opportunity scout**. They ask different questions; do not send three models the same “what wins?” prompt and count votes. Share initial reports only after the independent drafts exist. Then use an implementation-capable critic to test the strongest recommendation, not to conduct another broad idea search.

These are output requirements, not external token budgets or fixed research-minute allocations. Spend computation on source inspection and decisive experiments. Return concise conclusions plus inspectable supporting material; no mandatory report word count. Select one second-project direction, rather than implementing every promising idea in parallel. Preserve the existing submission work.

Actual event rules remain constraints: the live rules checked November 14 still give November 14 at 23:59 UTC as the submission deadline. They permit up to two independent, disclosed projects per person, and allow one project to select multiple genuinely fitting tracks. They list three prizes per track. Verify relevant rules at https://nearhackathon.com/HACKATHON.md rather than infer eligibility or judge preferences. State the deadline once in your reasoning; do not use it as a substitute for inspecting dependencies.

## Common instructions — paste with exactly one assignment

```text
You are an external specialist helping choose and strengthen a NEAR hackathon demonstration. We will use capable coding agents heavily. Evaluate concrete technical dependencies and the minimum convincing demonstration; do not assume normal solo-human implementation speed or require production readiness. Sophisticated work is allowed when its critical path is demonstrable. No invented numerical prize odds.

Verify live organizer rules at https://nearhackathon.com/HACKATHON.md. Use official docs, executable source, papers and first-person operator requests. Separate source claims, inspected code, executed observations and hypotheses. Commercial claims, README test counts and model agreement are not independent validation. Bounded failure to find demand is not proof that none exists.

Compare the strongest practical alternative with the same evaluator, evidence, trust and capabilities. We do not require monopoly novelty, paying customers, a published financial loss or an audit. A credible need and materially better integration, diagnosis, recovery, economics or user experience can justify a product. Emergent markets and organizer-suggested problems are eligible hypotheses, but label them honestly and identify an observable benefit.

Target a real end-to-end moment with an honest success control and a meaningful failure/attack. Labeled seeded failures, common-operator demo accounts and local/testnet simulations can be appropriate. State exactly what they demonstrate. Do not claim independent customers, live usage or production guarantees from them. Safeguards need to match the demonstrated money/authority claim, not an imagined enterprise deployment.

Inspect the critical integration or provide a safe local probe where possible. Report exact prerequisites: APIs, formats, verifier, evidence access, keys, approvals and licenses. Do not silently assume unavailable infrastructure or the correctness of generated code. Do not contact people, spend, deploy, publish or submit. Do not execute unreviewed third-party scripts with credentials. Never use Astra or launch nested agents without separate authorization.

Deliver REPORT.md with: recommended behavior and user; strongest baseline and concrete difference; primary-source evidence; runnable probe/result if executed; minimum demo and honest claim boundary; critical dependency and remaining work; strongest objection; and the next implementation action. Attach scripts/results needed to reproduce claims. A negative verdict is allowed. Supply one strongest recommendation and at most one runner-up, not an unranked idea catalogue.
```

## 1 — WBTS reconstruction: mechanism designer plus integration engineer

Give this agent the WBTS repo, including START-HERE.md and handoff/RESEARCH.md. Private chat history and the separate planning repository are unnecessary.

```text
Read the WBTS standalone handoff and relevant source. Investigate whether a substantially stronger, useful product can be built from it. Previous criticisms are challengeable evidence, not an instruction to keep or abandon the project.

Current core: NEAR contract/CLI with independently funded direct delegation edges, authenticated evidence, bonded allegations/challenges, deterministic input-versus-output findings, credits/release/withdrawal and scenario tests. Its only implemented evaluator rechecks integer fee splitting. It lacks a useful-work evaluator beyond that task, nested attribution and evidence UI. Unchallenged allegations may become final without checking evidence already stored at filing. Direct findings have no demonstrated capability advantage over escrow using the same evaluator. Cheap arithmetic, unproved monitoring economics and unvalidated practical demand caused the pause.

Find the strongest useful workflow and identify what accountability changes for its operator: acceptance, compensation, retry, recourse, diagnosis or access. Investigate alternatives to the exact original mechanism, including evaluating all filed claims, a useful second verifier, receipts/integration on existing escrow, explicit contractual recourse or nested obligations. Do not preserve optimism, bonds, nesting or architecture by default. Also do not remove them merely because an escrow could implement them.

Answer the escrow and always-check objections constructively. If retaining optimism, compare aggregate monitoring, evidence availability, disputes, capital/delay and wrong-outcome risk with the cheapest acceptable eager alternative. If changing it, state the new guarantee, financial consequences and code impact. Fault origin and contractual liability must remain distinct. More expensive answer generation is not by itself a verification advantage.

Select one workflow and inspect or run its critical evaluator/evidence path. Show the same useful case through the baseline and proposed design; identify the actual improvement. A fixture hash alone is not input validity, an arbitrary signed verdict is not execution proof, and passing tests is not general software quality. Prefer a decisive probe over more narrative. Historic coding-receipt, inference and policy-wallet investigations may be reopened when you bring new evidence, not just a new pitch.

Return a strongest revival design, a proposed first implementation slice with acceptance cases, and a precise account of reusable versus new parts. If no design earns a meaningful advantage, say so. Do not rebuild the complete marketplace or generic agent-verification universe merely to give the current mechanism a use case.
```

## 2 — Fresh swarm opportunity: coordination economist plus prototype engineer

This researcher need not read WBTS initially. Give it the common instructions and assignment, to avoid anchoring every opportunity to blame/escrow.

```text
Find a strong, fresh NEAR AI Swarms demonstration from an actual coordination problem. Do not assume it must be an escrow, wallet, reputation score or LLM chat group. Verify the official track wording and example: https://github.com/nearai/near-hackathon-prompt-examples/blob/main/tracks/05-swarms.md . Scripted strategies can establish economic behavior; LLM calls are not automatically the innovation.

Start from a specific job where several separately authorized actors have different information, preferences or incentives. Candidate problem families include aggregating small demands, allocating scarce work/resources, capacity commitments, cancellation/replacement coordination and settlement across participants. These are search directions, not validated recommendations. Seek first-person friction, documented integration gaps or a concrete organizer-supported hypothesis.

Explain why a single trusted coordinator or ordinary database/market software is insufficient at the intended trust boundary, and what NEAR actually enforces. Compare the same job and requirements. Do not invent a need for decentralization merely by splitting one script into agents. A common operator may run demo actors if disclosed; demonstrate the identities and incentive rules, not fictional customer independence.

Inspect the closest current implementation, including relevant market/delegation products. Espalier, Rootbound and FlashFirm are mandatory discovery leads when functionally relevant, not automatic grounds to reject the space. Show how the proposed user action/result differs. No speculative “empty lane” or “judges will love it” claim.

Choose one minimal end-to-end economic loop. Specify a happy path, a participant behaving strategically or disappearing, the effect on honest participants, actual contract/evidence requirements, and a visible outcome. Check mechanism pitfalls appropriate to the claim: splitting identities, collusion, false capacity, withheld bids, cancellation and recovery. Do not bolt on every conceivable defense or copy a marketplace feature list. A normal successful job must still work.

Inspect or prototype the hardest integration/rule. Return an evidence-backed problem, source-backed baseline difference, runnable critical probe if available, and the next buildable slice. Evaluate agent-assisted implementation from existing primitives and interfaces rather than asserting generic developer-day estimates. Explain whether the benefit is new capability, better economics or better workflow; any can count if demonstrated honestly.
```

## 3 — Track opportunity scout: contest analyst plus problem researcher

This scout compares opportunities, not every competitor's implementation. Its output can challenge track assumptions made by the other two researchers.

```text
Find where a credible additional NEAR demonstration has the strongest competitive opening. Treat track crowding as one input alongside strength of closest entries, user need, differentiation, NEAR contribution, dependency readiness and agent-assisted execution. Do not choose a track simply because its total is smallest.

Use the official public directory at https://nearhackathon.com/ and GET https://nearhackathon.com/api/projects?track=TRACK_ID&page=1 . Relevant ids: defi, thesis, privacy, business, swarms, security, agents, realworld, games, nfts, memecoins, social, open. Inspect current response schema and pagination; totals are overlapping labels, not unique eligible opponents or final results. Record retrieval time and uncertainty. A first-page sample cannot establish absence of close rivals; use targeted discovery/source checks for each eventual candidate.

As a starting snapshot only, November 14 05:06 UTC totals were: thesis 83; memecoins 95; games 120; nfts 121; social 124; swarms 140; defi 207; business 219; privacy 248; realworld 282; open 282; agents 514; security 545. Refresh if using them. Prize and judging claims require official evidence. No 3/N winning probabilities, assumption every prize must be awarded regardless of quality, or inference that broad multi-track tags equal substantive coverage.

Shortlist at most two lanes where a real need and agent-buildable demo coexist. One may be swarms; another may come from outside it. Investment Thesis is eligible for inspection because it is evidence-oriented and currently less populated, not a recommendation to manufacture a bullish thesis. A thesis needs a distinct reproducible empirical question, trustworthy data and an analytical contribution. Memecoin/game/NFT ideas need a meaningful mechanic or user loop, not a quick token/template relabeled for a smaller count. Avoid creating a new custody/proof/identity stack unless the dependency is genuinely ready.

For each shortlisted lane, propose one concrete product or research artifact and inspect its nearest strong public alternatives. State what is observed versus builder-claimed. Return the best opportunity and at most one runner-up, the baseline gap, a defensible track fit, critical runnable dependency/data probe, minimum demonstration and strongest rejection argument. Select all tracks a proposed product genuinely fits; do not add features only to qualify for extra labels.

Do not interpret rejecting new alternatives as proof WBTS is strongest. Do not recommend disrupting an existing submission without an explicit, concrete improvement. Return a decision-quality comparison, not a census or a market-size essay.
```

## Follow-up critic — only after independent results exist

Give an implementation-capable reviewer the reports, supporting artifacts and the relevant repo. Its job is to falsify recommendation-changing claims, not to vote or generate another list.

```text
Compare these proposed demonstrations. Identify the two or three claims whose failure would change the build choice. Independently inspect their primary sources and execute the available safe probes; report any missing artifacts. Check equal-capability baselines and the exact stated trust boundary. Do not inherit unsupported marketing, success counts or schedule claims.

Require a visible useful result, an honest success control, meaningful failure/attack evidence and a reproducible judge path. Do not require production infrastructure, mature adoption or unaided-human development speed. Separate implementation details coding agents can parallelize from external integrations/economic assumptions that still need evidence.

Return one recommendation with a concrete first build slice and its critical dependency. Name what would reverse it and any material human choices. If no candidate improves the submission case, say so. Do not average scores, invent probabilities or begin a new search/implementation automatically.
```

## Decision rule when reports return

Prefer the proposal with a useful demonstrated difference and a working critical path, rather than the strongest prose or most agents agreeing. A small integration win can beat an unimplemented grand mechanism. A sophisticated mechanism is welcome when its key path works. Preserve existing source/evidence; select one second-project direction before expanding implementation. Public release, spending, external messages, deployment and submission remain separate human authorizations.
